Solo AI-Engineering Consultancy — Phased Build Plan

Zero state → one-person consultancy running multiple concurrent projects on a stochastic-agents-inside-a-deterministic-harness paradigm, operable from any machine.

Budget  ~CAD $100/mo ceiling
Timeline  60 days
First workload  Practice / personal repo
Base  Ontario, Canada

0 · Assumptions & the single biggest risk

  • The proprietary planning model is pay-per-use, and the only fixed-ish cost accepted early. At practice volume (a few dozen plans/mo) it lands ~CAD $20–60/mo, leaving room under the ceiling.
  • The practice repo has real, runnable tests (or they get written first). No tests → no deterministic gates → the paradigm collapses into "trust the model."
  • The cheap, high-frequency OSS tier is bought per-token from managed providers (DeepInfra/OpenRouter), not run on the laptop — a laptop can't serve a capable 32B-class coding model.
  • "Any machine" means any machine with a browser + SSH/Tailscale — not carrying a GPU around.
  • 60 days is aggressive; achievable only because the first workload is a practice repo (no SLA) and everything is rented/pay-per-use, not built or owned.

⚠ Single biggest risk to the sequence

Building orchestration before a gate it can stand on actually works. The entire value of the paradigm is that quality is enforced by deterministic checks, not by trusting stochastic output. Wire up multi-agent orchestration while the acceptance / spec-conformance gate is still aspirational, and the agents produce plausible work that passes nothing real — burning the 60 days debugging agent behavior instead of trusting the harness. Gates first, every time. An agent role may only exist once the gate that judges its output is green-or-red on a real change.

The phases

1
The gate floorA CI pipeline that can definitively reject bad work — zero agents involved.
▾
Entry criteria
A practice repo exists with at least a handful of real unit tests and a runnable build.
Steps
  1. Wire local gates: linter (ruff/eslint), typecheck (mypy/tsc), unit tests (pytest/vitest). One command runs all, exits nonzero on any failure.
  2. Add an acceptance test layer — at least one end-to-end test of real behavior, not just units.
  3. Add a spec-conformance check: a written spec file per feature + a script that verifies the diff addresses the spec checklist. Start literal; don't model-ify it yet.
  4. Put it all in GitHub Actions (free tier) and turn on GitHub merge queue + branch protection — nothing merges without green gates.
  5. Deliberately submit a broken PR and confirm every gate fails. A gate you haven't watched fail is not a gate.
Stack & cost
GitHub Actions (free, 2,000 min/mo). Ruff/eslint/mypy/tsc/pytest (free). No model spend. Pay trigger: exceed 2,000 CI min/mo → move runners to the Phase 4 VPS before paying GitHub.
Exit criteria
At exit you can: push any change and have it provably accepted or rejected by lint + typecheck + unit + acceptance + spec-conformance gates, with the merge queue blocking everything that isn't green.
Attention budget
N/A — no projects yet. Pure tooling. Every minute here removes later attention cost: the gate, not you, becomes the arbiter of correctness.
2
One agent behind the gatesProve a single stochastic agent produces gate-passing work end-to-end; proprietary model only plans.
▾
Entry criteria
Phase 1 gates are green-or-red on a real change and the merge queue is enforcing them.
Steps
  1. Planning front-end: hand a feature request to the proprietary model (pay-per-use). It outputs a spec + decomposed task list — the judgment-heavy step. Keep it proprietary.
  2. Single executor: one capable OSS model via per-token API (DeepInfra/OpenRouter) takes one task + the spec and writes the implementation as a PR.
  3. Phase 1 gates run automatically. If red, failure output is fed back to the executor for one capped retry loop.
  4. You review the final PR before merge — heavy, intentional supervision to calibrate trust.
  5. Track what fraction of features clear the gates with the chosen model alone. That number drives Phase 3 tiering.
Stack & cost
Proprietary planning model — pay-per-use, ~CAD $20–50/mo at practice volume (downgrade: trivial/templated features → skip the proprietary call; upgrade: specs the executor can't satisfy → stronger planning tier). OSS executor — per-token (e.g. DeepSeek-V3.2 ≈ $0.25/M in, $0.38/M out), ~CAD $15–30/mo (upgrade: low gate-pass rate → stronger per-token model, still cheaper than GPU rental).
Exit criteria
At exit you can: take a one-paragraph feature request, get a proprietary-model plan, have a single OSS agent implement it, and merge only if every gate passes — reviewing just the final PR.
Attention budget · 1 project
High — you review every PR and most retry loops ("code-review every change"). Expected and temporary; you're buying calibration data, not scaling yet.
3
Tiered roles + orchestrationSplit the executor into decompose / implement / verify; tier each to the cheapest model that clears its gate; run the loop unattended.
▾
Entry criteria
Phase 2 produced several merged, gate-passing features, with data on per-task-type pass rate.
Steps
  1. Define three OSS roles behind the existing gates: decomposer (plan → atomic tasks), implementer (task → code), verifier (runs/interprets gates, writes missing tests to spec). Each role exists only because a gate already judges its output.
  2. Tier by difficulty: cheap per-token model for high-frequency, well-scoped tasks; escalate to a stronger model only when the cheap one fails a gate twice on the same task. Cheapest config that clears the bar wins.
  3. Write a thin orchestrator (a script / simple state machine — not a framework) driving plan → decompose → implement → verify → merge-queue, with hard caps on retries and spend per feature.
  4. Surface to you only two events: "plan ready, approve?" and "stuck — gate X keeps failing." Everything green flows to the merge queue automatically.
  5. Run a full practice feature through the whole loop untouched except plan approval.
Stack & cost
Add a stronger per-token escalation tier on the same provider — budget a CAD $15–25/mo cap enforced by the orchestrator's per-feature spend limit (upgrade: escalations on >~30% of tasks → cheap tier too weak, raise it; downgrade: escalations near zero → over-provisioned, lower the tier). Running total stays well under $100. No owned hardware, no rented GPU.
Exit criteria
At exit you can: approve a plan and walk away while tiered OSS agents decompose, implement, and verify it — the loop either lands a gate-passing PR in the merge queue or escalates one specific blocker.
Attention budget · 1 project
Medium — drops from "review every change" to "approve the plan + handle escalations." First phase where attention per project genuinely falls; it now attaches to decisions and exceptions, not every diff.
4
Control plane + machine-independenceMove orchestration off the laptop; drive everything from any machine with no local state that matters.
▾
Entry criteria
Phase 3's orchestrated loop reliably lands or escalates on the practice repo.
Steps
  1. Stand up a cheap always-on VPS as the control plane: orchestrator, secrets, queue state, logs. Execution plane stays ephemeral — CI runners or per-job VMs spun up and torn down.
  2. Move all secrets to the VPS / a secrets manager. Nothing sensitive lives on a laptop.
  3. Put the VPS on Tailscale (free tier) — reachable from any machine without exposing ports.
  4. All project state lives in git + the control-plane VPS. The laptop becomes a dumb terminal: SSH or a small web dashboard to approve plans and read escalations.
  5. Validate by driving a full feature from a different machine end to end.
Stack & cost
Control-plane VPS — Hetzner CX22 ~CAD $7/mo or Fly.io small (upgrade: orchestrating >~3 concurrent projects saturates it → bump size; downgrade: idle → smallest tier / scale-to-zero). Tailscale free. Self-hosted Actions runner here if past GitHub's free minutes. Running total ≈ CAD $7 + planning API + capped per-token OSS ≈ $45–80/mo. Still no owned GPU.
Exit criteria
At exit you can: open any machine with a browser, approve plans and clear escalations, and have the loop run on the always-on control plane with ephemeral execution — owning zero state locally.
Attention budget · 1 project
Same decisions as Phase 3, but location-independent — supervision cost per project doesn't rise, and you're no longer tethered to one machine being on. Bottleneck is firmly your attention, not hardware.
5
Consultancy ops: intake + parallel projectsRun multiple concurrent projects through one harness with attention that scales sub-linearly.
▾
Entry criteria
One project runs fully on the control plane, driveable from any machine.
Steps
  1. Intake: a standard template that turns an engagement into the artifacts the harness already eats — a spec, acceptance criteria, a definition of "done" mapped to gates. If intake can't produce gateable specs, the project isn't ready to start.
  2. Isolate per project: separate repo + branch-protected merge queue + per-project spend cap. One dashboard, N projects.
  3. Concentrate supervision at exactly two points per project: plan approval (front) and escalation handling (exceptions). Queue escalations across all projects so you triage by severity, not by project.
  4. Add a per-project spend + attention budget; consistently exceeding either is the trigger to raise rates or improve the harness — not to work more hours.
  5. Onboard a second practice project alongside the first; confirm the first's quality doesn't degrade.
Stack & cost
No new infra category — same VPS, planning API, capped per-token OSS, scaled by usage. Each added project adds marginal pay-per-use cost only, not a new fixed cost, until the VPS-size or CI-minute triggers fire. Stays near the ceiling only if project count is high — at which point billable revenue justifies raising it.
Exit criteria
At exit you can: run multiple concurrent client projects through one harness, supervising each only at plan-approval and escalation, from any machine.
Attention budget · N projects
Bounded and sub-linear in N. Per-project touch points are fixed at two (approve plan, resolve escalations) and don't grow as a project runs — gates carry verification. N projects ≈ N plan-approvals + a shared, severity-ordered escalation queue. The harness converts "review all the work" into "make the few decisions a machine can't."

The budget question: ~$100 vs ~$300/mo

The extra ~CAD $200/mo doesn't change the paradigm or the sequence — it moves three ceilings, and only one matters early.

1 · Higher concurrency / throughput headroom (the one that counts). Sustained per-token inference + a larger VPS let several projects run in parallel, fully off any single machine. This pulls Phase 5 concurrency forward.

2 · Looser per-feature spend caps → fewer artificial escalations (you stop bouncing to a human because the loop ran out of budget mid-feature). A direct, modest attention win.

3 · A bigger control plane sooner (~CAD $25–40/mo VPS) so 3+ concurrent projects don't saturate the box.

What it does NOT achieve: it doesn't justify owned GPU (rented still wins), doesn't move the gates-first sequence (Phases 1–3 are engineering/calibration-bound, not dollar-bound), and doesn't relieve the real bottleneck — your attention. Verdict: keep the $100 plan through Phases 1–3 unchanged; the extra $200 earns its place at the Phase 4→5 boundary, when a second real project is ready to run concurrently.

Why per-token inference, not RunPod or a local GPU

A laptop can't serve a capable 32B-class coding model, so the cheap/frequent tier is bought per-token from managed providers, not self-hosted. The models you'd want are already hosted there: DeepSeek-V3.2 ≈ $0.25/M input, $0.38/M output (USD). A full feature loop burns ~1–3M tokens ≈ $1–2; dozens of features/month stays well under $20.

RunPod is renting raw GPU — a different cost model. Serverless A100 ≈ $1.19/hr, H100 ≈ $3.25/hr, per-second with scale-to-zero. Great for sustained inference, but you manage the deployment and pay GPU wall-clock, not tokens. A persistent A100 pod 24/7 ≈ $850/mo — off the table. At practice volume a per-token API beats it decisively.

RunPod becomes the cheaper choice only when monthly per-token spend crosses what a mostly-utilized rented GPU would cost (rule of thumb: A100 serverless ~100 hrs/mo ≈ $120 ≈ 300M+ output tokens/mo — far beyond a practice repo). The one non-volume trigger that pulls it forward: client confidentiality — a contract forbidding shared third-party APIs forces isolated inference (a dedicated RunPod endpoint), and that cost is billable to the client.

Per-token prices move fast and providers churn — verify the exact model and rate when wiring it up, not from a number quoted today.

Machine-independence architecture

The control plane is a tiny always-on VPS (~CAD $7/mo) holding the orchestrator, secrets, queue/state, and logs; the execution plane is ephemeral — CI runners or per-job VMs spun up and destroyed by the orchestrator, holding nothing durable. All project state lives in git plus the control plane, never on a laptop. You reach the control plane over Tailscale and act through SSH or a small web dashboard whose only jobs are approve a plan and clear an escalation. Because no laptop holds secrets, state, or running processes, any machine with a browser is a full cockpit — and a lost or swapped laptop costs nothing but a re-login.
